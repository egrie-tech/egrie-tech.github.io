Self-hosting

Run the sync server yourself

The Android app is fully local without a server. A server only adds optional two-way encrypted sync and the audio-extraction endpoint (used for downloads and for in-app YouTube playback) — and it is plain Python with no Docker requirement, so a $5 VPS, a Raspberry Pi, or a box in your closet all work.

1. What the server is for

The supplied service provides three things: accounts and sessions, an end-to-end-encrypted sync log with encrypted checkpoints, and an optional audio-only YouTube extraction endpoint. Out of the box the app uses the operator's public instance at https://soundtrail.duckdns.org; running your own replaces that single URL and nothing else in your workflow changes.

The app encrypts each entity event and checkpoint on-device with AES-256-GCM before upload, and merges changes deterministically with a last-write-wins clock and a device-id tie-breaker, so the server is a durable relay rather than a content store. Pins, playlists, playlist songs, and automations sync both ways, including edits and deletions.

2. What the server can and cannot see

Visible to the serverNot visible to the server
Account email address, salted password hash, session tokens and expiry, request timing, source IP in proxy/server logs.Pin titles, notes, coordinates, playlist contents, song links, automation rules — all of it arrives as ciphertext.
Event IDs and sequences, ciphertext sizes, and per-account sync volume.The 256-bit recovery key, which never leaves the device.
For an extraction request: the single YouTube video ID you submit, plus the temporary audio file while it is served.Local audio files, imported music, provider credentials, mood descriptions, model requests, speech audio, and transcripts, none of which pass through the sync server.

End-to-end encryption of library content does not hide your account email, IP address, or traffic metadata. If you host the service for other people, those are the things they are trusting you with — along with whatever your reverse proxy logs.

3. Install and test locally

Start with a foreground run before making this public. The server needs Python 3.10 or newer and Git; it runs on Linux, macOS, Windows, and BSD. FFmpeg and a JavaScript runtime are optional and needed only for YouTube audio extraction.

  1. Clone the repository

    git clone https://github.com/mob5824m-wq/SoundTrail.git
cd SoundTrail/server
python3 --version

    Confirm the reported Python version is 3.10 or newer. On Windows, use py -3 in place of python3.

  2. Prepare the environment and run tests

    python3 run.py --setup
python3 run.py --test

    The launcher creates a private .venv and installs the pinned dependencies. The first setup needs internet access to download packages; later starts reuse the environment. --test runs the API test suite. If setup reports that venv or ensurepip is missing, install the matching Python venv package from your OS (for example, python3-venv on Debian/Ubuntu) and retry.

  3. Start the API and check it

    python3 run.py

    Leave it running, then open a second terminal on the same machine and check the health endpoint:

    curl -fsS http://127.0.0.1:8080/health

    A healthy server returns {"status":"ok","version":"v1"}. In Windows PowerShell, use Invoke-RestMethod http://127.0.0.1:8080/health. Stop the foreground process with Ctrl+C. It listens on 127.0.0.1:8080 by default; that is local-only and is the right setting when a reverse proxy runs on the same machine.

On Windows, run the same commands as py -3 run.py --setup, py -3 run.py --test, and py -3 run.py. Keep the terminal's working directory set to SoundTrail/server.

The default database file is server/data/soundtrail.sqlite3. The settings are PORT (default 8080), SOUNDTRAIL_HOST (default 127.0.0.1), and SOUNDTRAIL_DB (full path to a different SQLite file). For a service, choose a stable data path and ensure its parent directory is writable by the service account. Do not expose the Python port directly to the internet.

Optional: enable YouTube audio extraction

Sync works without these extras. For extraction, install FFmpeg on PATH. The launcher attempts to install the pinned Deno runtime for yt-dlp's YouTube challenge solver; if that wheel is unavailable for your platform, install Deno or Node.js on PATH. Extraction also needs outbound access to YouTube and temporary disk space. Re-test it after updating yt-dlp, because YouTube changes can break extraction.

4. Publish it behind HTTPS

The Android app requires an https:// server URL, so keep the API on loopback and put a TLS reverse proxy in front of it. This example uses Caddy on the same Linux host:

  1. Point a domain at the server

    Create an A record for your public IPv4 address (and an AAAA record only if IPv6 is correctly configured). Replace sync.example.net below with that hostname. Allow inbound TCP ports 80 and 443 in both the host firewall and any VPS/cloud firewall.

  2. Configure Caddy to proxy to the local API

    Install Caddy using the package for your operating system, then put this site block in /etc/caddy/Caddyfile. The repository's example Caddyfile contains the same configuration.

    sync.example.net {
    encode zstd gzip
    reverse_proxy 127.0.0.1:8080
}

    Replace sync.example.net with your DNS name. With public DNS and ports 80/443 reachable, Caddy obtains and renews the HTTPS certificate automatically. On a systemd install, validate and reload the config with:

    sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy

  3. Verify the public health check

    curl -fsS https://sync.example.net/health

    It should return {"status":"ok","version":"v1"}. If not, check DNS, firewall rules, Caddy's service log, and that the API is healthy at http://127.0.0.1:8080/health.

Never forward public traffic directly to port 8080. Configure the proxy to overwrite or sanitize client-supplied X-Forwarded-For before passing it upstream — the server trusts that header only when its direct peer is private or loopback, which is what makes per-IP limits meaningful. Keep proxy request-body and rate limits too, especially with multiple workers: the app's in-process limits reset on restart and apply per instance.

5. Keep it running, update it, and back it up

For a public Linux server, run the API as a dedicated unprivileged account and let systemd restart it after a reboot. The example below assumes a root-owned checkout at /opt/soundtrail, Python 3.10+ at /usr/bin/python3, and the Caddy proxy from section 4.

Linux: prepare the service account

If you have not already deployed the repository, clone it into the example location:

sudo git clone https://github.com/mob5824m-wq/SoundTrail.git /opt/soundtrail

Create separate writable locations for the database and Python virtual environment. The repository code can remain read-only to the service account; run.py needs write access to server/.venv to install its pinned packages.

sudo useradd --system --user-group --home-dir /var/lib/soundtrail --create-home --shell /usr/sbin/nologin soundtrail
sudo install -d -o soundtrail -g soundtrail -m 0750 /var/lib/soundtrail/data
sudo install -d -o soundtrail -g soundtrail -m 0750 /opt/soundtrail/server/.venv
sudo -u soundtrail /usr/bin/python3 -m venv /opt/soundtrail/server/.venv
sudo -u soundtrail /usr/bin/python3 /opt/soundtrail/server/run.py --setup
sudo -u soundtrail /usr/bin/python3 /opt/soundtrail/server/run.py --test

Change /opt/soundtrail if your checkout is elsewhere. Verify /usr/bin/python3 --version is 3.10 or newer before continuing. If creating the environment fails because venv support is missing, install the matching OS package (for example, python3-venv on Debian/Ubuntu). Install FFmpeg and a supported Deno or Node runtime system-wide if you want extraction; sync itself does not need them.

Create the systemd unit

Save this complete unit as /etc/systemd/system/soundtrail-sync.service:

[Unit]
Description=Soundtrail encrypted sync API
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=soundtrail
Group=soundtrail
WorkingDirectory=/opt/soundtrail/server
Environment=SOUNDTRAIL_HOST=127.0.0.1
Environment=PORT=8080
Environment=SOUNDTRAIL_DB=/var/lib/soundtrail/data/soundtrail.sqlite3
UMask=0077
PrivateTmp=true
NoNewPrivileges=true
ExecStart=/usr/bin/python3 /opt/soundtrail/server/run.py
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target

Load and start it, then check the service and local health endpoint:

sudo systemctl daemon-reload
sudo systemctl enable --now soundtrail-sync
sudo systemctl status soundtrail-sync --no-pager
curl -fsS http://127.0.0.1:8080/health

Use sudo journalctl -u soundtrail-sync -n 50 --no-pager to inspect startup errors. If health fails, check the log, database-directory ownership, Python version, and port conflicts. The database path in SOUNDTRAIL_DB must match the path you back up.

Updating the server

Back up the database first. For a root-owned checkout at /opt/soundtrail, pull the update as the checkout owner, refresh dependencies and run the tests as the service user, then restart:

sudo systemctl stop soundtrail-sync
cd /opt/soundtrail
sudo git pull --ff-only origin main &&
sudo -u soundtrail /usr/bin/python3 server/run.py --setup &&
sudo -u soundtrail /usr/bin/python3 server/run.py --test &&
sudo systemctl start soundtrail-sync &&
sudo systemctl status soundtrail-sync --no-pager

The && chain stops before restart if an update, setup, or test fails. If the health check then fails, stop the service and inspect the logs or restore the previous code and database backup.

Other operating systems

On macOS use launchd; on Windows use Task Scheduler or a service wrapper such as NSSM. Run python3 run.py (or py -3 run.py) with the working directory set to server, set the same SOUNDTRAIL_HOST, PORT, and SOUNDTRAIL_DB values, and run it as a non-administrator account. Keep the API bound to loopback when the TLS proxy shares the machine.

Back up and restore the database

Stop the service before archiving so SQLite is closed and its database and WAL side-files are captured together. Back up the directory containing the file set by SOUNDTRAIL_DB; for the systemd example above:

sudo systemctl stop soundtrail-sync
sudo tar -czf /secure-backups/soundtrail-data-$(date +%F).tar.gz -C /var/lib/soundtrail/data .
sudo systemctl start soundtrail-sync

Create /secure-backups as a private directory on a separate disk or backup target first. If you kept the default database location, stop the process and archive server/data instead. To restore, stop the service, keep a copy of the current data directory, and extract the archive into the parent directory of SOUNDTRAIL_DB. For the example path, restore ownership with sudo chown -R soundtrail:soundtrail /var/lib/soundtrail/data, then start the service and test a login/sync. Protect backups as private data and keep an off-host copy.

If the database is lost, only a backup restores the encrypted event log and checkpoints; users cannot rebuild it from device history, and a password reset does not recover the encryption key. The extraction endpoint also needs outbound network access to YouTube and enough temporary disk for up to two concurrent 250 MiB downloads plus working files. /health reports liveness only.

6. Limits, quotas, and the API surface

The database enforces a 64 MiB per-account quota for encrypted events and checkpoints, and snapshots are capped at 8 MiB. After a sync, event rows are pruned into the client's encrypted checkpoint and retry-receipt metadata goes with them, so an old delivery ID may be accepted again later — harmless because entity clocks and tombstones make duplicate old versions a no-op. Passwords are per-account salted scrypt hashes; session tokens are random, expire after 30 days, and are stored only as SHA-256 hashes.

RoutePurposeDefault in-process limit
POST /v1/accountsCreate account, return token5 / hour / IP
POST /v1/sessionsSign in20 / minute / IP
DELETE /v1/sessions/currentRevoke this session—
DELETE /v1/account/currentDelete account, sessions, events, receipts, checkpoint5 / hour / IP
GET /v1/events · POST /v1/eventsRead cursor + write encrypted events (1–500 per page)600 / minute / IP
POST /v1/snapshotsStore encrypted checkpoint, prune covered rows10 / minute / IP
POST /v1/youtube/audioOne video ID, rights flag, raw audio back30 / minute / IP, 20 / minute / account, 2 concurrent

There is deliberately no email verification, no password reset, and no key recovery endpoint. Extraction accepts exactly one YouTube video ID; playlists and general video downloads are not supported, and authorized: true is the caller's rights assertion, which the server cannot verify.

7. Point the app at your server

  1. Replace the URL

    In Soundtrail, open Connect → Cloud sync, put your public https:// URL in the Sync server URL field, and tap Create account and recovery key. A Use public server button resets the field to the default instance if you change your mind.

  2. Save the recovery key

    It is generated on the device and is the only way to decrypt your library on another one. A signed-in device can reveal it again; a new device needs the key itself, and uninstalling removes the local copy.

  3. Then add the second device

    Enter the same server URL, sign in, and enter the saved key. Automatic sync is off by default; Sync automatically when Soundtrail opens runs a sync at launch, which needs a signed-in account and this device's stored key. Retry sync re-runs the same merge after a failure, and Connect shows pending local changes.
